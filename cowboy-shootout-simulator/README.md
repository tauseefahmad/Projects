# Wild West Shootout Simulator

A Java simulation of the circular cowboy shootout described in the task,
producing a JSON protocol of every shot and a SHA-256 checksum of that
protocol file.

## How to run it

**In IntelliJ:** open this folder as a project (`File > Open`, select
`cowboy-shootout-simulator`), mark `src/main/java` as *Sources Root* if it
isn't picked up automatically, then create a Run Configuration for
`cowboyshootout.Main` with a program argument for the number of cowboys.

**From the command line:**

```
javac -d out $(find src -name "*.java")
java -cp out cowboyshootout.Main 8
```

Program arguments: `<numberOfCowboys> [randomSeed]`

- `8` – simulate 8 cowboys with a freshly generated random seed
- `8 42` – simulate 8 cowboys with a fixed seed (reproducible run, useful
  for testing/grading — this is exactly how `sample-output/` was produced)

The program prints the whole fight to the console, then writes
`protocol_<n>cowboys_<timestamp>.json` plus a `.sha256` sidecar file (in the
`sha256sum -c` compatible format) into the working directory, and prints
the checksum.

A pre-generated example lives in [`sample-output/`](sample-output) and
verifies with `sha256sum -c protocol_8cowboys_seed42.json.sha256`.

## Project structure

```
src/main/java/cowboyshootout/
  Cowboy.java            circle node: hp + prev/next links
  Direction.java          LEFT / RIGHT enum
  ShotRecord.java          one immutable protocol line (record)
  ShootoutResult.java       full outcome of one simulated fight (record)
  ShootoutSimulator.java     the game rules
  ProtocolWriter.java        JSON serialization + SHA-256 checksum
  Main.java                 CLI entry point
  FairnessAnalysis.java      Monte-Carlo tool used for the theory section below
```

## Design decisions (and why)

- **Circle = circular doubly linked list.** Each `Cowboy` node has `prev`
  and `next` pointers. "Closing the circle" after a kill is then a plain
  O(1) unlink (`target.prev.next = target.next; target.next.prev = target.prev;`)
  instead of shifting an array or list — it directly mirrors the physical
  picture of two neighbors stepping toward each other.
- **`java.util.Random` seeded explicitly, always reported.** Rather than
  relying on an unseeded generator, `Main` draws a seed from
  `SecureRandom` (or takes one on the command line) and seeds a single
  `Random` with it. The seed is written into the protocol's metadata, so
  any fight — "random" or not — can be replayed exactly. This is an
  existing JDK convenience (`java.security.SecureRandom`,
  `java.util.Random`), not a hand-rolled RNG.
- **Checksum via `java.security.MessageDigest`.** SHA-256 is computed with
  the standard JDK digest API over the exact bytes written to disk
  (`Files.readAllBytes` → `MessageDigest.digest`), formatted with
  `java.util.HexFormat`. No external crypto library needed.
- **Hand-rolled JSON writer, on purpose.** The protocol's shape is fixed
  and entirely generated by this program — the only strings in it are
  program-generated cowboy names, so there is no untrusted free text to
  worry about. A ~40-line writer with correct escaping (quotes,
  backslashes, control characters) is enough to guarantee valid JSON and
  keeps the project dependency-free, which matters for a program meant to
  just be opened and run in IntelliJ without a build tool pulling
  artifacts from the network. (Swapping in `org.json`/Gson/Jackson would
  be a five-minute change if a project build tool is added later — the
  writer is fully isolated in `ProtocolWriter`.) The output was verified
  against `python3 -m json.tool` (strict JSON parser) and validates as
  well-formed.
- **Records for `ShotRecord` / `ShootoutResult`.** Both are pure,
  immutable data carriers with no behavior — a natural fit for Java
  records instead of classes with manual constructors/getters/`equals`.
- **`ShootoutSimulator.run(seed, recordProtocol)`.** The protocol-recording
  flag exists so `FairnessAnalysis` can run hundreds of thousands of
  fights for statistics without allocating millions of `ShotRecord`
  objects it would immediately discard.

## Protocol format

Each shot is one JSON object:

```json
{
  "shotNumber": 13,
  "shooter": "Cowboy-4",
  "shooterHp": 8,
  "direction": "RIGHT",
  "target": "Cowboy-5",
  "damage": 3,
  "targetHpBefore": 3,
  "targetHpAfter": 0,
  "targetKilled": true
}
```

covering exactly what the sheriff asked for (who fired, who was hit, HP
lost, HP remaining), plus a few extra fields (shooter's HP, direction,
kill flag) that make the record self-contained and let anyone re-derive
the whole fight — including *why* that direction was chosen — without
re-running the program. `metadata` (seed, cowboy count, HP settings,
starting shooter) and `result` (winner, total shots) frame the shot list.

## Is the game fair? (theory + data)

**Short answer: no.** The rule "even HP → shoot right, odd HP → shoot
left" is not a coin flip — it's a deterministic function of the *shooter's*
current HP. Randomness only enters through (a) who starts, and (b) the
1–5 damage rolls. That's enough structure to create a real, measurable
bias:

1. **The first shot is never random.** Every cowboy starts at HP = 10,
   which is even. Whoever is drawn as the starting shooter therefore
   *always* shoots right — 100% of the time, not by chance. His immediate
   right-hand neighbor is guaranteed to be the very first person shot at,
   before a single random damage roll has happened. Confirmed empirically
   below ("First shot went RIGHT" = 100.00% across 20,000 sampled fights,
   independent of cowboy count).

2. **Kill streaks snowball in one direction.** When a shot kills its
   target, the *same* active cowboy shoots again — and since his own HP
   didn't change, his direction (parity) doesn't change either. So a
   cowboy who starts a kill streak keeps mowing down cowboys in the *same*
   direction until he finally fails to land a killing blow. Once someone
   gets a favorable run of high damage rolls against already-weakened
   neighbors, they can clear several seats in a row (visible in
   `sample-output/protocol_8cowboys_seed42.json`, shots #13–15: Cowboy-4
   kills three neighbors back to back). This is a positive feedback loop,
   not a symmetric process.

3. **HP carries over and never resets**, so a cowboy who survived an
   earlier hit is more likely to die on the next one — position in the
   circle interacts with *when* a cowboy's turn comes around again, which
   is itself a side effect of the deterministic direction rule.

Because of (1) and (2), a cowboy's fate depends heavily on **where they
sit relative to the randomly chosen starter**, not just on luck applied
equally to everyone. To turn that into a number rather than just
intuition, `FairnessAnalysis` runs large Monte-Carlo batches and tracks
win rate by seat offset from the starter (offset 0 = the starter, offset
1 = the starter's right-hand neighbor = the very first target, and so on
around the circle):

```
8 cowboys, 300,000 trials
  offset starter    :   7.55%  (expected if fair: 12.50%)
  offset starter+1  :   3.45%  (expected if fair: 12.50%)   <- first victim, worst odds
  offset starter+2  :  10.24%  (expected if fair: 12.50%)
  offset starter+3  :  15.28%  (expected if fair: 12.50%)
  offset starter+4  :  18.06%  (expected if fair: 12.50%)   <- best odds
  offset starter+5  :  18.07%  (expected if fair: 12.50%)   <- best odds
  offset starter+6  :  15.60%  (expected if fair: 12.50%)
  offset starter+7  :  11.75%  (expected if fair: 12.50%)
```

The same shape shows up at 6 and 12 cowboys (see below): the starter's
immediate right-hand neighbor wins only about **a third to a half** of a
fair share, the starter himself is also below average, and the cowboys
sitting roughly *opposite* the starter (a few seats further around the
circle) win noticeably more than their fair share.

```
6 cowboys, 300,000 trials              12 cowboys, 300,000 trials
  starter    : 13.08% (fair 16.67%)      starter    :  3.02% (fair 8.33%)
  starter+1  :  5.88% (fair 16.67%)      starter+1  :  1.55% (fair 8.33%)  <- worst
  starter+2  : 16.01% (fair 16.67%)      starter+2  :  4.99% (fair 8.33%)
  starter+3  : 22.19% (fair 16.67%)      starter+3  :  8.29% (fair 8.33%)
  starter+4  : 23.20% (fair 16.67%)  <-  starter+6  : 13.34% (fair 8.33%)  <- best
  starter+5  : 19.65% (fair 16.67%)      ...
```

**Conclusion:** the game is not fair. The cowboy *least* likely to win is
whoever ends up seated directly to the right of the randomly-chosen
starter — they take the one guaranteed, non-random first shot before the
game has produced any other information, and are therefore effectively
already "one hit down" relative to everyone else. The cowboys with the
best odds are the ones seated roughly across the circle from the starter,
far enough away that they are unlikely to be reached early by a kill
streak coming from either side, while still being close enough to
eventually inherit the active role once streaks fizzle out. Since the
starter is chosen uniformly at random each game, no single *named* cowboy
(e.g. "Cowboy-3") has a fixed edge over a large number of games — but
within any single game, the seating position relative to that game's
starter is a real, quantifiable predictor of who is most likely to walk
away.

Reproduce these numbers yourself:

```
java -cp out cowboyshootout.FairnessAnalysis 8 300000
```
